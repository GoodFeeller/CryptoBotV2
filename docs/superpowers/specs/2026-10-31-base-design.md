# CryptoBot v2: база

Дата: 2026-10-31. Статус: на ревью.

## 1. Цель и границы

Проект: бот на TypeScript для торговли USDT-перпетуалами Bybit. Код находит рыночные ситуации, например подход цены к сильному уровню. Claude решает, что с ними делать: входить ли, в какую сторону, по какой цене, с каким плечом и суммой, где стоп и тейк. Раз в час Claude ведёт открытую сделку.

Цель всего проекта: медианная доходность от +60% в месяц при просадке до 50%, подтверждённая бэктестом. Достижимость цели неизвестна, её покажут бэктесты.

Порядок этапов: **база → уровни → сигналы → демо-счёт**. Каждый этап получает свою спеку и свой план.

**Этот документ описывает только базу.** Она включает:

- данные Bybit и отбор топ-10 монет;
- модуль Claude API;
- модуль Telegram с картинкой сделки;
- движок сделок и защиту от просадки;
- бэктест и бумажный режим на живых данных.

**В базу не входят:** поиск уровней, настоящие сигналы, настоящие ордера на бирже, сохранение открытых сделок между перезапусками. Базу можно запускать только с заглушкой сигналов, поэтому её результаты ничего не говорят о доходности.

Числа, помеченные в этом документе как «по умолчанию», задаются в конфиге. Это начальные значения, не результат исследований.

## 2. Архитектура

Один движок работает и в бэктесте, и вживую. Он зависит только от интерфейсов, а реализации подставляются при сборке.

```text
src/
  core/                 типы и интерфейсы, без внешних зависимостей
  features/
    market-data/        Bybit: монеты топ-10, свечи, фандинг, кеш на диске
    claude/             запросы, ответы, проверка, кеш, обезличивание
    telegram/           тексты сообщений и отправка
    chart/              картинка сделки
    signals/            заглушки детектора, позже настоящие сигналы
    risk/               защита от просадки и расчёт объёма
    trading/            движок: жизненный цикл сделки
    backtest/           симулятор биржи, прогон, отчёт
  app/
    config.ts           чтение и проверка конфига
    backtest.ts         сборка и запуск бэктеста
    live.ts             сборка и запуск бумажного режима
```

Правила:

- `core` ничего не импортирует из проекта.
- Фичи импортируют только `core`, друг друга не импортируют. Проверяется командой `npm run check` через `dependency-cruiser`.
- Реализации собираются только в `app`.
- В каждой папке фичи есть `README.md`: что делает, что принимает, что отдаёт, от чего зависит, как тестируется.

## 3. Поток работы

Движок работает шагами по закрытию свечи исполнения (`executionTimeframe`, по умолчанию 5m). На каждом шаге строго по порядку:

1. **Исполнение на свече:** брокер проверяет лимитные ордера, стопы и тейки на только что закрывшейся свече и начисляет фандинг. Открытые и закрытые сделки уходят в Telegram.
2. **Защита от просадки:** обновляется пик капитала и просадка.
3. **Разбор сделок:** для каждой открытой сделки, где с открытия прошло кратное 60 минутам время, вызывается `reviewTrade`.
4. **Поиск входов:** если закрылась сигнальная свеча (`signalTimeframe`, по умолчанию 1h), детектор проверяет монеты топ-10.
5. **Отложенное исполнение:** решения шагов 3 и 4 исполняются по открытию следующей свечи.

Вход:

```text
ситуация → RiskGate → монета свободна и есть лимит позиций → расчёт допустимой потери → Claude
         → проверка ответа → Broker.placeLimit
         → следующая свеча: post-only → ордер исполнен → сделка открыта → Telegram
```

**По рынку бот не входит.** Вход только лимитным post-only ордером. Сторону, цену, плечо, сумму, стоп и тейк выбирает Claude. Для лонга цена ниже текущей, для шорта выше, поэтому вход на пробое по цене выше текущей для лонга невозможен: он исполнился бы сразу как taker.

Если на следующей свече ордер исполнился бы сразу как taker, либо цена, стоп и тейк перестали проходить проверку из раздела 5, ордер не выставляется.

Выставленный ордер отменяется, если:

- за `limitOrderTtlHours` (по умолчанию 4) он не исполнился;
- цена дошла до тейка раньше входа, то есть движение прошло без нас;
- сработала защита от просадки.

Claude не разбирает неисполненные ордера: ежечасный разбор начинается с момента исполнения. Отмены не идут в Telegram, но попадают в отчёт.

Ограничения: одна позиция или ордер на монету, в сумме не больше `maxPositions` (по умолчанию 5). Ордер занимает место и резервирует маржу до исполнения или отмены.

Сделка закрывается только по стопу, тейку или решению Claude. Лимита по времени нет. В конце бэктеста оставшиеся сделки закрываются по последней цене с причиной `end_of_run`.

### Список монет

Список фиксирован в конфиге (`symbols`) и меняется вручную: BTC, ETH, SOL, XRP, DOGE, 1000PEPE, SUI, HYPE, ADA, FARTCOIN. Это топ-10 USDT-перпетуалов Bybit по обороту за 2 года, отобранный один раз 31.10.2026.

**Известное ограничение:** список выбран по сегодняшнему дню, поэтому в бэктесте он знает будущее: в него попали монеты, которые к этой дате выросли по обороту и не были сняты с торгов. Результат на истории из-за этого может быть завышен. Монета до даты запуска просто не торгуется.

## 4. Модуль Bybit

Публичный API v5, ключи не нужны: `/v5/market/instruments-info`, `/v5/market/kline`, `/v5/market/funding/history`.

- Свечи и фандинг кешируются на диске в `data/`. Повторный запрос за закрытый период не идёт в сеть.
- Ошибки сети и лимитов: до 5 повторов с нарастающей паузой, затем ошибка наверх.
- Перед сохранением проверяется непрерывность свечей. Дыра в данных записывается в отчёт, значения не выдумываются.

## 5. Модуль Claude

Официальный SDK `@anthropic-ai/sdk`. Модель задаётся в конфиге, по умолчанию `claude-opus-5-5`. Ключ `ANTHROPIC_API_KEY` берётся из `.env`. Точные параметры запроса и способ получения структурированного ответа определяются в плане по актуальной документации API.

### Обезличивание

В запросе нет тикера и дат, иначе модель может узнать период и вспомнить, что было дальше.

- Цены приведены к шкале «последнее закрытие = 100».
- Объём приведён к среднему за переданное окно.
- Свечи идут от старых к новым, без времени.
- Ответ приходит в той же шкале и пересчитывается обратно в код.

Этот же формат используется вживую. Окна свечей задаются в конфиге, по умолчанию 200 свечей 1h и 100 свечей 4h. Значения уточним на этапе сигналов.

### Запросы и ответы

| Запрос | Что получает Claude | Что отвечает |
|---|---|---|
| `decideEntry` | тип ситуации, текущая цена (всегда 100 в шкале), уровни и индикаторы ситуации, допустимая потеря в % капитала, свечи | `enter`, `side`, `entryPrice`, `leverage`, `notionalPct` (сумма сделки в % капитала), `stop`, `take`, `reason` |
| `reviewTrade` | сторона, вход, стоп, тейк, текущий результат в R, часы в сделке, свечи | `newStop` или null, `newTake` или null, `closeNow`, `reason` |

Системный промпт хранится в `features/claude/prompts/` и имеет номер версии. В базе это простой черновик, настоящий промпт трейдера пишем на этапе сигналов и сравниваем версии бэктестами.

### Проверка ответов кодом

Ответ проверяется схемой `zod`, затем правилами.

Вход (значения по умолчанию):

- цена входа с правильной стороны от текущей: лонг ниже, шорт выше;
- стоп и тейк с правильной стороны от цены входа;
- стоп не ближе `minStopPct` (0.3%) к цене входа;
- при срабатывании тейка сделка остаётся в плюсе после комиссий и проскальзывания;
- потеря при стопе с издержками не больше допустимой потери;
- плечо не выше предела монеты на бирже;
- маржа (`сумма / плечо`) не больше свободного капитала;
- при таком плече ликвидация дальше стопа: `расстояние до стопа < 1 / плечо − maintenanceMarginPct`.

Фиксированного соотношения тейка к стопу нет: Claude ставит тейк и стоп по рынку, у каждой сделки своё соотношение.

Разбор:

- `closeNow = true` важнее остальных полей;
- новый стоп только уменьшает риск: для лонга выше текущего, для шорта ниже, и остаётся с правильной стороны от цены;
- новый тейк можно двигать в обе стороны, но он остаётся с правильной стороны от цены.

Негодный ответ не применяется. Если стоп негодный, а тейк годный, не применяется весь ответ.

### Сбои

- Ошибки 429 и 5xx: до 3 повторов.
- Вход при сбое или негодном ответе: сделка не открывается, в Telegram уходит ошибка.
- Разбор при сбое или негодном ответе: стоп и тейк остаются прежними, в Telegram уходит ошибка.
- Если в бэктесте таких сбоев больше 1% запросов, прогон прерывается: результат перестал бы отражать работу Claude.

### Кеш и расходы

- Ключ кеша: SHA-256 от модели, версии промпта и тела запроса. Кешируются только успешные ответы. Так повторный прогон даёт те же решения и ничего не стоит.
- Кеш работает только в бэктесте. Вживую каждый запрос идёт в API.
- Стоимость считается по токенам из ответа API и ценам из конфига.
- `claude.budgetUsd` ограничивает новые траты за прогон. По достижении лимита прогон прерывается со статусом `budget_exceeded` и не выдаёт вердикта.
- `backtest --estimate` до старта показывает число сигналов и оценку стоимости, не обращаясь к Claude.

### Бэктест через сессии Claude Code

Бэктест не обращается к платному API: решения принимают отдельные сессии Claude Code. Запрос к API остаётся для `live`.

`SessionDecisionAdvisor` работает так:

1. Прогон доходит до запроса, ответа на который нет в хранилище `data/decisions/<промпт>/`.
2. Все запросы текущего шага записываются в `pending/<ключ>.json`: системный промпт и обезличенное тело, та же схема ответа. Прогон завершается со статусом `needs_decisions`.
3. Сессия читает файлы и записывает ответы в `answers/<ключ>.json`.
4. Прогон запускается заново. Готовые ответы подставляются из хранилища, прошлые шаги повторяются без обращения к сессии, и прогон доходит до следующих запросов.

Ответы зависят от прошлых сделок, поэтому раздать весь период сразу нельзя: запас потери и разборы сделок известны только после предыдущих шагов.

Сессия работает вслепую: в отдельной папке без репозитория, данных и инструментов поиска, видит только файлы запросов. Ответ проходит те же проверки кода. Негодный ответ считается сбоем так же, как в API.

Отчёт хранит источник решений `decisionSource: session | api`. Сессия Claude Code и запрос к API могут отвечать по-разному, потому что отличаются системное окружение и настройки модели. Перед демо-счётом часть решений нужно сверить через настоящий API.

### Сравнение без Claude

`RandomSideAdvisor` на каждую ситуацию детерминированно выбирает случайную сторону и применяет фиксированные параметры из конфига `baseline`: отступ входа, стоп, тейк, сумму и плечо. Сделки он не меняет. Отчёт по нему сравнивается с прогоном Claude на том же периоде: это показывает, зарабатывает ли Claude больше случайного выбора, и позволяет запускать конвейер бесплатно.

## 6. Риск

**Объём:** `qty = баланс × notionalPct / 100 / цена входа`, округление вниз до шага монеты. Если объём ниже минимума биржи, сделка не открывается. Сумму и плечо выбирает Claude, код только проверяет их.

**Допустимая потеря:**

```text
допустимая потеря = maxDrawdownHaltPct − текущая просадка − потери при стопах открытых сделок и ордеров
```

Все величины в % от пика капитала. Если результат не больше нуля, Claude не вызывается. Предела на одну сделку нет: Claude может поставить на сделку весь запас.

**Защита от просадки (`RiskGate`):** просадка считается от пика капитала с учётом незакрытого результата. При достижении `maxDrawdownHaltPct` (по умолчанию 40%) новые сделки не открываются, неисполненные лимитные ордера отменяются, открытые сделки ведутся как обычно. Автоматического снятия нет: в бэктесте запрет действует до конца прогона, в бумажном режиме до перезапуска. Срабатывание попадает в отчёт и в Telegram.

## 7. Бэктест

### Симулятор биржи

| Что | Правило |
|---|---|
| Выставление ордера | на открытии следующей свечи; если ордер исполнился бы сразу, post-only его отклоняет |
| Вход | по цене ордера, без проскальзывания, комиссия maker; только если цена прошла ордер минимум на `limitFillThroughPct` (по умолчанию 0.02%), простого касания мало; гэп в нашу сторону не улучшает цену |
| Вход и стоп в одной свече | считаем, что вход исполнился и стоп сработал |
| Вход и тейк в одной свече | вход исполнился, тейк в этой свече не засчитывается |
| Стоп | по цене стопа; при гэпе по цене открытия, если она хуже; плюс проскальзывание, комиссия taker |
| Тейк | по цене тейка, без проскальзывания, комиссия maker; гэп в нашу сторону не улучшает цену |
| Стоп и тейк в одной свече | считаем, что сработал стоп |
| Закрытие решением Claude | открытие следующей свечи плюс проскальзывание, комиссия taker |
| Изменение стопа и тейка | действует со следующей свечи |
| Фандинг | по историческим ставкам Bybit, от объёма позиции, в момент начисления |

По умолчанию: taker 0.055%, maker 0.02%, проскальзывание 0.05% на сторону, `maintenanceMarginPct` 0.5%. Ликвидация отдельно не моделируется, потому что вход с ликвидацией ближе стопа отклоняется. Исключение это гэп за стоп и ликвидацию: сделка считается закрытой по цене открытия свечи.

### Отчёт

Файлы в `data/runs/<id>/`: `report.json`, `trades.csv`, `equity.csv`, снимок конфига. Краткая сводка в консоли.

Содержание: доходность по календарным месяцам и медиана, максимальная просадка, число выставленных ордеров, доля исполненных, отмены по причинам, результат упущенных входов (что было бы при входе рынком в ту же сторону с теми же стопом и тейком), распределение сторон, плеча и сумм, число сделок, доля прибыльных и доля безубыточности при фактическом соотношении, средняя прибыль и средний убыток в R, средний результат в R, комиссии, проскальзывание, фандинг, расходы и число запросов Claude, число изменений стопа и тейка и ранних выходов, сбои, срабатывание защиты, дыры в данных.

### Вердикт

Режим задаётся флагом:

- `research`: подбор параметров, вердикт `N/A`.
- `validation`: проверка на отрезке, который не участвовал в подборе.

`PASS` ставится, только если всё верно:

- режим `validation` и детектор не заглушка;
- минимум 6 полных календарных месяцев;
- издержки включены;
- медианная доходность за месяц не ниже +60%;
- максимальная просадка не выше 50%.

Иначе `FAIL`, либо `N/A`, если не выполнены первые три условия. Прогоны `validation` сохраняются в `data/runs/validation-log.csv`, чтобы было видно, сколько раз проверялся один отрезок: многократная проверка превращает его в подбор.

## 8. Telegram

Сообщения на русском, отправка через Bot API, `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` из `.env`.

| Тип | Содержание | Картинка |
|---|---|---|
| Открыта сделка | монета, лонг/шорт, сигнал, вход, стоп, тейк, причина от Claude | да |
| Закрыта сделка | монета, лонг/шорт, сигнал, результат в USDT и R, причина закрытия, вход, стоп, тейк, выход | да |
| Сделка отредактирована | монета, что изменилось в формате «было → стало», причина от Claude | нет |
| Ошибка | где, что случилось, что бот сделал дальше | нет |

Картинка: свечи, линии входа, стопа и тейка, у закрытой сделки точка выхода. Строится своим кодом в SVG и переводится в PNG через `@resvg/resvg-js`.

Сбой Telegram (3 повтора) пишется в лог и не останавливает торговлю. Если не построилась картинка, сообщение уходит без неё. В бэктесте используется `NullNotifier`.

## 9. Режимы запуска

```bash
npm run backtest -- --from 2026-01-01 --to 2026-07-01 --mode research
npm run backtest -- --from 2026-01-01 --to 2026-07-01 --mode research --estimate
npm run backtest -- --from 2026-01-01 --to 2026-07-01 --mode research --advisor session
npm run backtest -- --from 2026-01-01 --to 2026-07-01 --mode research --advisor random-side
npm run live
npm run notify-test
```

`notify-test` отправляет в настоящий чат по одному сообщению всех 4 типов на настоящих свечах с пометкой «тест». Ошибку нельзя дождаться по расписанию, поэтому без этой команды её не проверить.

`live` работает на настоящих свечах с настоящими Claude и Telegram, но сделки идут через симулятор и средств не касаются. Открытые сделки при перезапуске теряются, это ограничение снимем на этапе демо-счёта. Настоящих ордеров в базе нет.

## 10. Конфиг и логи

- `config/default.json`: все настройки, проверяются `zod` при старте. При ошибке бот не запускается.
- `.env`: только секреты, в git не попадает. В репозитории лежит `.env.example`.
- Логи в JSON-строках: каждый запрос к Claude, ответ, результат проверки и действие.

## 11. Заглушки сигналов

Детектор выдаёт `Situation`: монету, тип, время, уровни и индикаторы. Стороны, цены входа, стопа и тейка в ней нет, их выбирает Claude.

- `EveryNCandlesDetector`: ситуация каждые N сигнальных свечей, без уровней. Нужен, чтобы прогнать конвейер целиком.
- `ScriptedSignalDetector`: ситуации из списка, только для тестов.

У обоих `isPlaceholder = true`, поэтому вердикт по ним всегда `N/A`.

## 12. Тесты

Стек: Node 22, TypeScript в строгом режиме, ESM, `vitest`, `tsx`. Тесты пишутся до кода и не ходят в сеть. `npm run check` запускает типы, тесты и проверку зависимостей.

Обязательно покрыть:

- **Заглядывание в будущее:** изменение свечей после момента T не меняет ни одного решения до T.
- **Симулятор:** исполнение лимитного ордера при касании и при проходе цены, отклонение post-only, вход и стоп или тейк в одной свече, стоп и тейк в одной свече, гэпы, комиссии, проскальзывание, фандинг для лонга и шорта.
- **Движок:** порядок шагов, частота разбора от момента исполнения, все причины отмены ордера, занятое ордером место в лимите позиций, закрытие в конце прогона.
- **Claude:** каждое правило проверки, обратный пересчёт шкалы, отсутствие тикера и дат в теле запроса, кеш, лимит бюджета, порог сбоев.
- **Риск:** расчёт объёма и допустимой потери с учётом открытых сделок и ордеров, округление, отклонение по потере, марже, плечу и ликвидации, срабатывание защиты.
- **Отбор топ-10:** не использует данные текущего дня, исключает стейблкоины и молодые монеты.
- **Отчёт:** медиана месяцев и все ветки вердикта.
- **Telegram:** тексты всех 4 типов, сбой отправки не останавливает движок.
- **Воспроизводимость:** два прогона на одних данных и кеше дают одинаковый отчёт.
- **Сквозной тест:** бэктест с заглушками всех внешних API проходит от данных до отчёта.

## 13. Готовность базы

База готова, когда:

1. `npm run check` проходит.
2. Реальный бэктест на топ-10 с `EveryNCandlesDetector` на небольшом отрезке с лимитом бюджета завершается и выдаёт отчёт с вердиктом `N/A`.
3. Повторный запуск того же прогона не тратит деньги на Claude и даёт тот же отчёт.
4. `npm run notify-test` присылает в Telegram все 4 типа сообщений с настоящими данными.
5. `npm run live` запускается на живых данных и проходит минимум один цикл поиска входов и разбора без ошибок.

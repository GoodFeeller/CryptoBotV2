# CryptoBot v2: план реализации базы

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Собрать базу бота: данные Bybit, Claude, Telegram, движок лимитных сделок, защиту от просадки, бэктест и бумажный режим. Настоящих сигналов и ордеров нет.

**Architecture:** Один движок зависит только от интерфейсов `core`. Фичи не импортируют друг друга и собираются в `app`. Бэктест и `live` отличаются часами, источником свечей и уведомителем, а брокер в обоих случаях симулятор.

**Tech Stack:** Node 22, TypeScript strict, ESM, `tsx`, `vitest`, `zod`, `@anthropic-ai/sdk`, `@resvg/resvg-js`, `dependency-cruiser`, `dotenv`.

**Spec:** `docs/superpowers/specs/2026-10-31-base-design.md`

## Global Constraints

- Вход только лимитным post-only ордером. По рынку входа нет.
- Значения по умолчанию: `executionTimeframe` 5m, `signalTimeframe` 1h, `maxPositions` 5, `maxDrawdownHaltPct` 40, `maintenanceMarginPct` 0.5, `minStopPct` 0.3, `limitOrderTtlHours` 4, `limitFillThroughPct` 0.02, taker 0.055%, maker 0.02%, проскальзывание 0.05% на сторону, окна Claude 200×1h и 100×4h.
- Фиксированного соотношения тейка к стопу нет. Тейк обязан оставлять сделку в плюсе после издержек.
- `core` ничего не импортирует из проекта. Фичи импортируют только `core`. Реализации собираются только в `app`.
- В каждой папке фичи `README.md`: что делает, что принимает, что отдаёт, от чего зависит, как тестируется.
- Тесты пишутся до кода и не ходят в сеть. Сообщения Telegram на русском.
- Claude: `client.beta.messages.parse`, модель `claude-opus-5-5`, `output_config: { effort: "high", format: zodOutputFormat(schema) }`, `max_tokens` 16000, `maxRetries` 3, `betas: ["server-side-fallback-2026-07-01"]`, `fallbacks: "default"`. Параметры `temperature`, `thinking: disabled`, `budget_tokens` и prefill не использовать: на этой модели они дают 400.
- Цены Claude в конфиге, $ за 1M токенов: вход 4, выход 20, чтение кеша 0.20, запись кеша 5.
- Числа времени в мс UTC. Цены `number`, округление до шага монеты только на границе брокера.

**Уточнения интерфейсов спеки**, принятые при планировании: `Broker.close` не возвращает сделку, а ставит закрытие в очередь на следующее открытие; все исполнения приходят через новый метод `Broker.poll()`; в `MarketData` добавлен `instrument()` для шагов цены и объёма.

## Изменения после начала работы (важнее текста задач ниже)

Решение пользователя: бот отдаёт Claude только ситуацию, свечи и допустимую потерю. Сторону, цену входа, плечо, сумму, стоп и тейк выбирает Claude.

- **Типы (новый блок в `core`):** `Signal` заменяется на `Situation { symbol; kind; at; levels: { price: number; touches: number }[]; indicators: Record<string, number> }`. `EntryRequest { situation; currentPrice; candles; maxLossPct; }`. Успешный `EntryDecision` дополняется полями `side`, `leverage`, `notionalPct`. `Equity.usedNotional` заменяется на `usedMargin`. В `Position` и `LimitOrder` добавляется `leverage`. В `Instrument` добавляется `maxLeverage`. Новый `Exposure { lossAtStop: number }`. `PositionSizer`, `SizingInput` удаляются, `SizingResult` остаётся для `sizeFromNotional`.
- **Task 2:** `risk` содержит только `maxDrawdownHaltPct`. В `costs` добавляется `maintenanceMarginPct: 0.5`. Новая секция `baseline { entryOffsetPct: 0.2, stopPct: 1, takePct: 1.5, notionalPct: 20, leverage: 5 }`.
- **Task 4:** `RiskGate.availableLossPct(equity, exposures)` по формуле из раздела 6 спеки, `sizeFromNotional(balance, notionalPct, entryPrice, instrument): SizingResult`. Ограничения плечом и `riskPct` больше нет.
- **Task 6:** детекторы возвращают `Situation` без стороны и цен.
- **Task 7:** `validateEntry` проверяет все правила раздела 5 спеки, включая потерю, маржу, плечо и ликвидацию. Тело запроса содержит уровни и индикаторы в той же шкале цен. Индикаторы-цены масштабируются, поэтому имена индикаторов с ценой начинаются с `price:`.
- **Task 8:** перед вызовом Claude движок считает допустимую потерю и не вызывает его при значении ≤ 0.
- **Task 9:** вместо `PassThroughAdvisor` пишем `RandomSideAdvisor(baseline)`, сторона по хешу `symbol + at`, флаг `--advisor random-side`.
- **Task 3:** отбора топа в коде нет. Список монет фиксирован в `symbols` конфига. Из `MarketData` убраны `topSymbols` и `listInstruments`, движок и прогон берут монеты из конфига. Файла `top-symbols.ts` нет.
- **Task 12:** отчёт показывает распределение сторон, плеча и сумм, а также `decisionSource`.
- **Task 10:** добавляется `SessionDecisionAdvisor(store, cfg)`: при отсутствии ответа пишет `pending/<ключ>.json` и бросает `DecisionsNeededError`. Ключ тот же `cacheKey`, вместо модели значение `session`. Тесты: `missing answer writes pending and stops`, `all requests of one step are written together`, `existing answer is replayed and validated`, `invalid answer counts as failure`, `pending body has no symbol and dates`.
- **Task 13:** флаг `--advisor session`, статус `needs_decisions`, в консоль выводятся путь к запросам и их число. Тест: `rerun after answers continues past the previous stop and gives the same earlier trades`. Режим `claude` остаётся для сверки и `live`.

## Review Focus

- У монеты пустая или короткая история свечей: монета пропускается в этом шаге, прогон продолжается (Task 8).
- Неполные первый и последний месяцы прогона: не входят в медиану и в счётчик полных месяцев (Task 12).
- Баланс упал так, что объём ниже минимума биржи: ордер не ставится, нет деления на ноль и падения (Task 4).
- Повреждённая строка кеша Claude или свечей: строка игнорируется, данные запрашиваются заново (Tasks 3, 10).
- Telegram отвечает 429 с `retry_after`: отправитель ждёт указанное время, затем повторяет (Task 11).

### Task 5: Симулятор биржи

**Files:**
- Create: `src/features/backtest/simulated-broker.ts`, `src/features/backtest/README.md`
- Test: `tests/features/backtest/simulated-broker.test.ts`

**Interfaces:**
- Consumes: `Broker`, `Candle`, `FundingRate`, типы сделок.
- Produces: `new SimulatedBroker({ initialBalance, costs, clock }) implements Broker`, `feed(symbol: string, candle: Candle): void`, `feedFunding(symbol: string, rate: FundingRate): void`, `orderHistory(): OrderRecord[]`, `closedTrades(): ClosedTrade[]`, `closeAll(reason: 'end_of_run'): void`. `OrderRecord = { order: PendingOrder; firstCandleOpen: number | null; outcome: 'filled' | CancelReason | 'open' }`.

Порядок обработки в `feed` для одной свечи:

```text
1. Очередь закрытий: исполнить по open ± проскальзывание, комиссия taker.
2. Новые ордера, это их первая свеча: если open пересекает цену ордера → cancelled(post_only).
3. Ордера с истёкшим expiresAt → cancelled(expired).
4. Ордера: если цена прошла ордер на limitFillThroughPct → filled по цене ордера, комиссия maker.
   Иначе, если свеча дошла до тейка → cancelled(take_reached).
5. Позиции, включая открытые на этой свече:
   стоп задет → закрыть по стопу или open, если он хуже, плюс проскальзывание, комиссия taker.
   Иначе, если позиция открыта не на этой свече и тейк задет → по тейку, комиссия maker.
```

Если свеча задела и ордер, и тейк ордера, порядок внутри свечи неизвестен, поэтому считаем исполнение: это консервативный вариант.

`pnl` включает комиссии, проскальзывание и фандинг. `r = pnl / (qty × |entryPrice − initialStop|)`. Фандинг: лонг платит при положительной ставке, шорт получает.

  - `stop and take in same candle → stop`.
  - `stop gap fills at open when worse`; `take gap fills at take, not better`.
